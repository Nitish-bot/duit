## Problem Statement

Individuals with a mixture of routines, dated obligations, flexible work, and someday Tasks need a trustworthy way to understand their own days and, when they choose a Partner, stay gently aware of each other and offer encouragement without turning care into surveillance. Existing task tools commonly become noisy, guilt-inducing, visually generic, overly collaborative, or unreliable when recurrence, offline edits, privacy changes, device replacement, time zones, and Android reminder restrictions interact.

Duit must make each person's day feel manageable while preserving calendar, ownership, privacy, and history truth. It must remain useful without a connection, synchronize safely when connectivity returns, restore after uninstall or phone loss, and deliver reminders as reliably as Android permits. Approved Members may use Duit unpaired; paired Members may see only the Tasks each Owner explicitly shares and may send lightweight encouragement. Duit is not a shared-work management platform and not a safety-critical alarm system.

## Solution

Build Duit as a polished native Android task manager centered on a personal Today, supported by a separate Together view, a week-first Plan view, and a complete Tasks library. Users compose understandable timing and repeat choices instead of selecting technical task types. Recurring Series, Series Revisions, generated Occurrences, persisted outcome state, and Schedule Exceptions remain distinct so that future edits never rewrite past work.

Duit works offline after one online Google sign-in and administrator approval per Member. Each Member has an independently owned private workspace and normally uses one primary phone. Many independent Pairs may coexist, but each optional Pair contains exactly two distinct approved Members and a Member may belong to at most one active Pair. Every Task starts Private and keeps one immutable Owner; only that Owner may explicitly create `Shared(pairId, shareGeneration)`. The Partner may read only the resulting redacted Shared View and cannot mutate canonical Task state. Cloud Firestore provides durable storage, persistent local caching, queued writes, and clean-device recovery without a second Room database or custom synchronization engine.

The experience uses a warm botanical identity, restrained motion, short meaningful celebrations, humane language, and no streaks, scores, punishment, comparison, or engagement loops. Preset Cheers support affection without comments, nudges, read receipts, or automatic activity alerts. Local Task reminders are selective, exact when Android grants access, transparently approximate otherwise, and rebuilt after relevant device and application events; generic FCM notifications announce synchronized Cheers only.

## Implementation Decisions

- Build a native Android application named Duit with application ID `com.gaylord.duit`, `minSdk 28`, and the stable Android 16 / API 36 compile/target toolchain. Test API 37 compatibility but adopt it only after its SDK, AGP, and dependencies are stable. Confirm the target phone models before physical-device acceptance; one known target is a recent OnePlus Nord.
- Start with one Android Gradle `:app` module. Maintain deep internal packages for application composition, domain model/recurrence, Firestore data, authentication/pairing, reminders/encouragement, export, design system, and the Today, Together, Plan, Tasks, editor, and settings features. Keep the shared Pairing server handler under `supabase/functions/` (deployed as a Supabase Edge Function, ADR-0007) and its Node emulator host and tests under `functions/`; extract another Android module only after measured build or reuse pressure.
- Use Kotlin, Jetpack Compose, Material 3 foundations with Duit-specific tokens, Coroutines, Flow, Navigation Compose, ViewModel, DataStore, WorkManager, AlarmManager, Firebase Cloud Messaging, and a version catalog/Firebase BoM. Do not add Room, analytics, an RRULE library, or a general-purpose backend in v1.
- Establish one primary product-behavior seam named `DuitWorkspace`. It accepts Member-level commands and exposes observable personal Agenda, Together, Task detail, history, Pair, Cheer, sync, and reminder state. ViewModels use this boundary rather than Firebase or schedulers directly. Commands cover Pair Invite/mutual confirmation/Unpair, creation and Visibility, revision, one-occurrence override, planning, Focus, Subtask progress, Complete, direct outcome correction, Skip, Remove Occurrence, pause/resume, end/archive, Cheer, and restore.
- Use a small manual dependency container with constructor injection and a custom Worker factory. Inject clock, zone provider, ID generator, `DuitWorkspace` dependencies, persistence gateway, and reminder gateway so scenario tests control time and platform effects.
- Model Task as a stable identity with exactly two variants, Standalone Task and Recurring Series. Model immutable effective-dated Task Revisions and Series Revisions, generated Occurrences, interacted Occurrence State, and Schedule Exceptions as distinct domain concepts. A completed Occurrence State maps to a Completion Record; grouping progress and the mutually exclusive outcome in one persisted record makes direct correction atomic.
- Model approved Member, optional Pair, Partner, immutable Task Owner, Task-wide `Private | Shared(pairId, shareGeneration)` Visibility, prospective Share Grant, redacted Shared View, Completion Epoch, and Cheer as separate domain concepts. Each Member owns a private workspace independently of Pairing. A Pair is an access relationship between exactly two distinct approved Members, not shared Task ownership; many independent Pairs may coexist, but a Member may belong to at most one active Pair. Only the Owner mutates canonical Task state; a Partner's only cross-owner write is their own deterministic preset Cheer on a valid current-generation target.
- Every Task starts Private, before and during Pairing. The always-visible **Only me / Share with [Partner]** control requires an explicit Owner choice to create `Shared(pairId, shareGeneration)`. Unpair ends that Pair ID permanently, leaves both independently owned workspaces intact, and causes all old Shared bindings to behave as Private; either Member may later form a new Pair, which inherits no Task access or Cheers.
- Keep Today, Plan, Focus, Needs a decision, local reminders, and resolved-day state personal. Together is a separate read-only destination showing the Partner's Shared Tasks for today, the next seven days, at most ten date-level completions from seven days, and all Shared Tasks. It omits negative outcomes, metrics, presence, exact times/zones, and Partner freshness; only generic offline copy and the sender's own pending Cheer are allowed.
- A Private-to-Shared transition starts a new prospective Share Grant and publishes a whitelisted Shared View: title, note, Subtask labels, schedule, current/future actionable state, and date-level completions recorded during that grant. Exclude reminders, Focus, checked Subtask progress, negative outcomes, corrections, exact action times/zones, and diagnostics. Shared-to-Private works offline and revokes server reads after synchronization but cannot retract viewed content or securely overwrite a disconnected cache; disclose that limit.
- Store canonical Task history Owner-only and maintain deterministic current-generation Shared View projection documents in the same offline write batches. Re-sharing creates a new generation, so older Private history and Cheers never reappear. The projection is rebuildable read data, never another editable Task or source of truth.
- Allow one preset Cheer per sender/target with deterministic identity, Completion/Share generation, replace/remove/Undo, offline queueing, no self-Cheer, and no free text, reply, read receipt, count, or score. Open-work Cheers are limited to current/future actionable Tasks or Occurrences; completion Cheers target a valid Completion Epoch. Negative/paused/ended/archived targets are ineligible. `Allow Cheers`, local dismissal, and push mute are separate recipient controls. Only the first eligible Cheer per target in a rolling 24-hour window may push; replacement/removal/tombstones update in-app state only.
- Use a purpose-built pure Kotlin recurrence algebra: daily intervals anchored to start date; weekly intervals anchored to the ISO Monday week with selected weekdays; monthly intervals anchored to start YearMonth with selected month days; yearly intervals anchored to the start year with selected MonthDay values; common bounds; additions, removals, moves, overrides, and Pause Spans. Do not persist RRULE or support nth/business-day rules in v1.
- Derive an Owner-local Occurrence key from Task identity and Nominal Date; every cross-account target additionally includes `ownerUid`. Moving changes Effective Date but never identity. Future canonical Occurrences are generated for bounded windows and are not persisted indefinitely.
- Store calendar commitments as `LocalDate`, reminder clock values as `LocalTime`, and actual Owner actions as `Instant` plus observed zone/local date. Format clock values from each device's current 12/24-hour preference at display time and react to setting changes; presentation never mutates the stored `LocalTime` or scheduled reminder semantics. Future work follows the Owner device zone. DST gaps use the first valid later instant; overlaps use the earlier offset and post once. Shared dates stay literal; Pair profile publishes only the Owner's current `LocalDate`, never a raw zone or activity timestamp.
- Implement the locked humane semantics: literal missing dates are skipped; series edits are This occurrence or This and future using Nominal Date boundaries; Pause Spans imply summarized Skips; End series preserves history; Let it pass and Keep it open are per-series; stale Anytime plans return to Anytime; a flexible Planned Date that passes before Deadline returns to Could do; overdue fixed/deadline work remains in Needs a decision; moving an overdue flexible Task explicitly moves plan and Deadline together; Not Doing terminates only a Standalone Task; Skip resolves one recurring Occurrence; Archive ends an active Recurring Series before hiding it.
- Apply one Task-state resolution precedence: Remove Occurrence; explicit outcome; Pause Span by Nominal Date; one-occurrence move/content override; Series Revision default; Miss Policy derivation. Resolve Owner-only reminder revisions/overrides separately after Effective Date. Reject Added Occurrence when its Nominal Date already exists. The earlier of an inclusive rule end date and an exclusive End series boundary wins, but explicit persisted outcomes remain visible in Owner history.
- Permit direct history correction of outcome, completion instant, and checked Subtask state only. Keep title, notes, Nominal Date, Effective Date, and definition snapshot read-only. Clearing an explicit outcome recomputes Pause and Miss Policy derivations; Complete-to-Skip and Skip-to-Complete are atomic replacements.
- Use warm botanical light/dark tokens, original non-mascot illustration contracts, and tiered non-blocking celebrations. Do not enable dynamic color by default because it would replace Duit's deliberate identity.
- Use Firebase Authentication through Android Credential Manager and separate development and production Firebase projects. Google sign-in establishes identity only; a server-controlled `memberApprovals/{uid}` record with `approved == true` is also required before any workspace data is readable or writable. Administrator approval is manual for now and scales to any number of Members. Pairing is optional; each active Pair contains exactly two distinct approved Members, and a Member may belong to at most one active Pair.
- Use Cloud Firestore as the sole persisted Task store. Its durable cloud documents are the recovery source and its Android persistent cache is the offline operational store. Configure a bounded 100 MiB cache rather than unlimited retention, enable local indexes, and install listeners through repositories.
- Scope owned data under each UID. Nest Owner-only canonical Revisions, Occurrence States, Exceptions, and Pause Spans under their parent Task alongside separately authorized `sharedDefinitions`, `sharedExceptions`, `sharedCompletions`, bounded 30-day `cheerTargets`, and per-Task Cheers. Rules authorize a Cheer through a current target document instead of evaluating recurrence. Keep effective-dated reminder records, Daily Plans, Focus, settings, restore state, device tokens, and sync diagnostics Owner-only; expose only a narrow active-Partner profile containing display identity, current `LocalDate`, and `allowCheers`. Store Pair lifecycle separately with deterministic server-owned per-UID membership locks; keep `memberApprovals/{uid}`, hashed Pair Invites, persisted invite-rate limits, and Cheer-delivery ledgers server-only.
- Use offline-persisted Firestore write batches for related canonical and Shared View changes, normally scoped to one Task. Do not make core behavior depend on Firestore transactions because they fail offline. Start restore batches at ten writes and raise the cap only after Emulator tests prove Security Rules access-call budgets; never assume Firestore's 500-write limit is usable with cross-document rule checks.
- Accept whole-document last-write-wins for mutable Occurrence State, Focus, and settings under the one-primary-phone-per-Member invariant. A Partner is never a second Task writer. Append immutable child Revisions for definition edits; detect sibling children as a rare fork, follow the active pointer that won synchronization, retain both branches, and keep device/edit/branch diagnostics in Owner-only documents. Choosing a branch creates a new resolving Revision. Never let a stale delete resurrect an entity.
- Hydrate a replacement installation with explicit server reads for the Member's complete canonical owner tree before enabling editing. Hydrate Pair membership, Shared Task envelopes, and only current-generation Shared View/Cheer documents separately so a Together failure cannot block personal work. Failure of owner hydration keeps editing locked and offers Retry or Sign out; only completed server reads may establish a truly empty workspace. After hydration, core owner behavior works from persistent cached state and queued writes.
- Aggregate Firestore snapshot metadata and write failures into On device, Backing up, Backed up at, and Needs attention states. Together may show only a generic offline/out-of-date state plus the sender's own pending Cheer, never Partner freshness. Pending writes never block ordinary offline Task actions. Require connectivity for account switching/sign-out so pending writes and this installation's FCM token registration are removed before clearing authentication, Credential Manager state, and Firestore persistence. On observing Unpair, enter a non-editable `RevokingPairData` state, hide Partner content, stop listeners, reject new commands, fully drain pending writes, then clear the entire Firestore cache and rehydrate Owner data; never call `clearPersistence()` with queued writes.
- Deny Firestore access by default and require both an authenticated UID and its server-controlled Member Approval with `approved == true`. Google Authentication alone grants no workspace access. An unapproved identity may read only its own approval record so the app can explain the state; it may read or write no workspace, Task, Pair, or other Member data. Permit an approved Owner access from the path UID even when an offline Shared binding's Pair has since ended; normalize it to effective Private after sync. Permit Partner reads only for the Shared envelope/current-generation projection of an active exact Pair, with query constraints because Rules are not filters. Deny canonical/reminder/diagnostic reads and all cross-owner writes except a tightly validated current-generation Cheer. Former Partners may read only their ended Pair tombstone while they remain approved Members.
- Use Auth- and App Check-protected callable Functions with server transactions for short-lived one-use Pair Invite creation, two-sided identity confirmation, and irreversible termination of that Pair during Unpair. Contend on both deterministic membership locks and persistent rate-limit documents; reject self-pairing, expired/replayed codes, concurrent acceptance, already-paired Members, a third Member, and unapproved accounts. Either former Partner may later form a new Pair, whose Pair ID inherits no old access. These online relationship commands are the only deliberate exception to offline Task writes.
- Configure Firebase App Check with Play Integrity for outside-Play distribution: register the release signing certificate, do not require Play-recognized/licensed verdicts, monitor both sideloaded builds, then enforce Firestore and callable Functions. Use the debug provider only against the development project.
- The Pairing backend is a Supabase Edge Function on the free plan, not Cloud Functions, so Blaze billing is not required for development (ADR-0007). Revisit hosting, free-tier pausing and the service-account secret before production.
- Allow one configured base reminder and at most one active alarm per Occurrence. Later replaces that alarm rather than adding another. Fixed and recurring reminders use Effective Date; flexible reminders use Planned Date when present, otherwise Deadline; setting an Anytime reminder also assigns a Planned Date.
- Use one-shot AlarmManager alarms, exact-and-allow-while-idle when special access is granted and inexact allow-while-idle otherwise. NotificationManager posts/cancels. WorkManager performs daily 30-day alarm and Shared View/Cheer-target horizon reconciliation plus idempotent Done actions, never exact timing or Firestore synchronization.
- Reconcile alarms after every relevant domain edit, completion/outcome change, app start, boot, date/time/zone change, exact-access change, and package replacement. Validate cached current state before posting and suppress obsolete reminders.
- Provide Done and repeatable one-hour Later notification actions. Completion writes through Firestore's offline queue. No repeated overdue nags; the morning summary is opt-in and inexact.
- Use FCM only for optional Encouragement notifications. A Firestore-triggered Function revalidates Pair/Share Grant/target/Allow Cheers and consults a server-only idempotency/cooldown ledger. Only an eligible first Cheer sends; replacement/removal/tombstones do not. The generic payload contains `recipientUid`, IDs, and a preset ID, never Task content. Before posting, require `recipientUid` to equal the current Auth UID and the Pair/grant to remain active; use a stable Android notification ID and re-authorize on open. Firestore—not FCM—is Cheer truth. Never push automatic completion, overdue, Missed, Skip, reschedule, Focus, or inactivity events.
- Disable Android Auto Backup for v1 and explicitly exclude Firestore, auth/install state, DataStore, and scheduler state. Firestore is normal recovery; manual export is the independent mechanism.
- Define `.duitbackup` as versioned, unencrypted UTF-8 JSON selected through the Storage Access Framework. Warn **This unencrypted file contains your complete Task data and history**. Export only Owner canonical/reminder/settings records; exclude derived Shared View data, Partner-owned cache, Pair membership/Invites, Cheers, profiles, diagnostics, and device tokens. Restore only into an empty owner workspace after full validation/preview and coerce stale Shared bindings to Private unless the same active Pair is explicitly confirmed. Starting restore persists a restore-session ID/progress; stable Task-scoped batches may resume that session, while a different import into the now non-empty workspace is rejected.
- Version every persisted document and backup. Tolerate additive fields, reject unsupported future versions, and require a successful export before a destructive migration.
- Distribute release APKs with one stable signing key stored securely in two independent locations. Handle package replacement by rebuilding reminders.
- Build the first vertical slice as one Shared Daily Task across two paired test accounts: mutually confirmed Pairing with membership locks, offline Owner creation/completion/undo/correction, personal Today, redacted current-generation Together, one non-inferable Private control, Completion Epoch, one Subtask label without Partner progress, one Owner-only reminder, one eligible queued Cheer plus single generic FCM, synchronization, privacy revocation, non-editable Unpair cache cleanup, process/reboot survival, and clean-device Owner restore. Do not expand Task types until its security, recovery, and reminder drills pass.

## Testing Decisions

- A good test observes behavior at the highest stable boundary: submit user-level commands, advance an injected clock/zone, observe resulting Agenda/history/sync/reminder state, and assert durable externally meaningful outcomes. Do not test private helpers, Compose implementation structure, Firestore DTO internals, or exact animation frames.
- The primary seam is `DuitWorkspace`. Deterministic in-memory persistence, Pair, notification, and reminder adapters drive most user stories through one scenario harness, including offline mode, process-style reconstruction, canonical/Shared View hydration, Pair/membership lifecycle, Share/Completion generations, Cheer eligibility/races/cooldowns, date boundaries, direct outcome correction, total outcome/exception precedence, revision scopes/fork resolution, humane projections, restore sessions, and idempotent command replay.
- The pure recurrence engine is the one deliberate lower seam because its combinatorial calendar space needs property/table tests that would be opaque through UI scenarios. Cover every interval type, anchors, bounds, leap years, days 29–31, deterministic keys, DST conversion, zone/date-line travel, move collisions, revision boundaries, Pause Span precedence, and exception composition.
- Firestore repository and Security Rules conformance use the Firebase Emulator. Test approved Owner CRUD; Partner access only to explicitly shared current-generation Shared View/Cheers; an identity's self-read but no listing or client writes of Member Approval; denial of canonical/reminder/diagnostic, Private, old-generation, ended-Pair, cross-Pair, outsider, unauthenticated, and unapproved workspace data; every query constraint; maximum rule-access-cost batches; offline stale-binding writes; reconnect/replay; last-write-wins; Revision fork detection; tombstones; schema evolution; malformed/oversized documents; and immutable fields. Use at least two simultaneous Pair fixtures to prove isolation while retaining the exactly-two-Members-per-Pair invariant.
- Shared View contract tests prove reminder data, raw zones/exact instants, checked Subtask progress, Missed/Skip/Not Doing/Remove, corrections, and diagnostics never enter partner-readable documents, while Private Tasks create no placeholders, counts, empty-state discrepancy, or activity hint.
- Emulator Suite tests (Auth and Firestore, with a Node host for the Pairing handler) cover approved and unapproved identities, self-invite, mutual identity confirmation, expired/replayed code, persisted attempt cooldown, simultaneous acceptance against membership locks, already-paired/third-Member attempts, Unpair followed by a different Pair, multi-Pair isolation, Unpair races, invalid Cheer target/preset/generation, duplicate/out-of-order triggers, replacement/tombstone cooldown suppression, and stale FCM tokens.
- Reminder domain scheduling is tested through the injected reminder gateway at the `DuitWorkspace` seam. Android conformance tests separately cover exact access grant/denial/revocation, notification denial, stale-alarm suppression, Done/Later while offline, boot, clock/zone changes, 12/24-hour preference changes without reminder drift, package replacement, process death, and the 30-day horizon. FCM tests cover token rotation, current-Auth recipient matching, lost/duplicate/cooldown delivery, generic content, no replacement/tombstone push, stable notification replacement, and deep-link authorization after privacy revocation.
- Compose tests assert visible behavior and accessibility semantics for Today ordering, maximum-three Focus, fast add defaulting to Only me with the audience visible before submission at 200% text, mutual Pairing review, capped Together/redacted read-only details, Cheer eligibility/Undo/dismiss/Allow Cheers/mute, exact neutral Unpair and generic freshness copy, device-derived 12/24-hour display changes, edit-scope prompts, Needs a decision actions, direct history correction, permission rationale, sync labels, and restore progress. Do not snapshot every pixel.
- Physical OnePlus tests are release gates for screen-off exact/inexact delivery, Doze, reboot, OxygenOS battery optimization, notification actions, APK replacement, and force-stop diagnostics.
- Recovery conformance includes airplane-mode creation/edit/completion/Visibility change, Partner stale-cache disclosure and convergence, reconnect until Backed up, clean-install canonical/current-generation Together hydration, duplicate prevention, history fidelity, reminder rebuild, the `RevokingPairData` no-new-writes guarantee, Unpair/account-switch full cache clearing, and disclosure of unrecoverable never-synchronized edits.
- Backup tests cover round trip, empty and large datasets, the ten-write initial Rules budget, malformed JSON, unsupported versions, invalid dates/enums/IDs, interrupted/repeated restore, non-empty-workspace rejection, exclusion of projection/Pair/Partner/Cheer/diagnostic data, and stale Shared-to-Private coercion.
- Accessibility acceptance covers TalkBack roles/actions/order, 48dp targets, 200% font scale, light/dark contrast, reduced motion, non-color status cues, and visible alternatives to all gestures.
- There is no prior test suite because the repository is greenfield. The first Shared Daily Task vertical slice establishes the reference scenario harness, redacted projection contract, approved multi-account Rules/Emulator Suite pattern, Compose semantics pattern, and physical-device release checklist that later features must copy.

## Out of Scope

- Multiple simultaneously active devices per Member as a normal workflow; shared Task ownership; Partner editing/completion; assignment; custom per-field/Occurrence audiences beyond the fixed Shared View; Partner access to exact activity or negative-outcome history; Pairs with more than two Members or more than one active Partner per Member; comments, chat, or team workspaces.
- Medical, emergency, medication, or other safety-critical reminder guarantees.
- Guest mode, anonymous local-only workspaces, account-linking merges, or sign-in-optional operation.
- Projects, folders, tags, priorities, attachments, rich text, independent Subtask schedules/reminders, dependencies, or nested Subtasks.
- Arbitrary RRULE/cron expressions, nth weekday, business-day calendars, natural-language recurrence parsing, or calendar import/export.
- Streaks, XP, productivity scores, leaderboards, social feeds, activity/presence tracking, nudges, punitive copy, repeated overdue nagging, or engagement analytics.
- A mascot, audio celebrations by default, dynamic-color-first branding, or animation that ignores reduced-motion preferences.
- Biometric app locking, screenshot blocking, hidden-app mode, custom lock-screen redaction, or encrypted manual backup in v1.
- Android Auto Backup as a Task recovery path, server functions beyond Pair lifecycle/Cheer fan-out, a general-purpose custom backend, Room, or a custom synchronization engine.
- Google Play publication, subscriptions, billing, monetization, web/desktop clients, widgets, Wear OS, or third-party integrations.
- Search until observed task volume justifies it; Tasks filters and the week-first Plan view are sufficient for v1.

## Further Notes

- The canonical product promise is: manage your own day, share by choice, encourage without pressure, and leave.
- The glossary terms—especially Pair, Member, Partner, Owner, Visibility, Shared, Private, Share Grant, Shared View, Completion Epoch, Cheer, Together, Occurrence, Nominal Date, Effective Date, Planned Date, Deadline, Skip, Remove Occurrence, Missed, Focus, Anytime, and Needs a decision—are normative.
- Six architectural decisions are accepted: Firestore is the only persisted Task store; recurrence uses the purpose-built model rather than RRULE; conflict handling optimizes for one primary phone per Member; Pair-scoped redacted Shared Views never create shared Task ownership; minimal Functions/FCM handle trusted Pair lifecycle and rate-limited Cheer notification delivery; and per-UID administrator approval admits individual Members while Pairing remains optional.
- The five highest risks are cross-account privacy leaks, calendar correctness, unproven owner-only recovery, unreliable Android alarm/FCM delivery, and Together becoming surveillance or scope creep.
- Architecture readiness requires target phone models/versions, a confirmed application ID, stable API 36 toolchain, a development Firebase project with initial approved-Member records, later production Firebase plus Pairing-backend hosting/FCM/App Check setup, securely duplicated signing material, frozen recurrence/Shared View/generation/membership/Rules-access/schema/backup contracts, approved Today/Together/privacy/Cheer/notification design, and scripted multi-account offline/privacy/Unpair/re-pair/reboot/zone/12-24-hour/update/restore drills.
- The first implementation milestone is not complete until one explicitly Shared Daily Task and one default-Private non-inferable control survive Shared View redaction, approved/unapproved and cross-Pair Rules/Functions checks, airplane mode, process death, reboot, Cheer loss/duplication/cooldown, privacy revocation, frozen-edit Unpair cleanup, synchronization, and clean-device Owner restoration with no duplicate Occurrence, leaked Private data, repeated push, lost pending write, or stale reminder.
